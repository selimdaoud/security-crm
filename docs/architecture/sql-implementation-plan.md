# sed-dashboard SQL Implementation Plan

## Purpose

This document defines the SQL implementation plan for the `sed-dashboard` MVP on an OCI Oracle APEX workspace.

The goal is to create a clean, repeatable database foundation for:
- Security Advisor portfolio dashboard.
- Customer and contact management.
- Oracle estate tracking.
- Interactions, reviews, and actions.
- Security cases and security events.
- Customer impact assessment.
- Notification campaigns.
- Relationship health scoring and snapshots.
- Alerts and dashboard reporting.

This is an implementation plan, not the final SQL code.

## Design Principles

Use these principles when writing the SQL scripts:

- Keep the MVP schema simple and advisor-focused.
- Use `security_cases` as the operational object for impact assessment and campaigns.
- Keep `security_events` as source/detail records that can be grouped into a case.
- Store current customer health directly on `customers`.
- Store health history in `relationship_health_snapshots`.
- Keep email sending manual in the MVP.
- Use lookup tables for values shown in APEX lists of values.
- Use foreign keys for core relationships.
- Add indexes for dashboard filters and joins.
- Use `generated by default on null as identity` for surrogate primary keys.
- Use `varchar2` for codes and names, `clob` for long text, `date` or `timestamp` for dates.
- Add audit columns consistently.

Create the SQL scripts in this order:

1. `01_drop_objects.sql`

3. `03_core_tables.sql`

## Naming Standards

### Tables

Use plural lower-case names:
- `customers`
- `customer_contacts`
- `security_cases`
- `notification_campaigns`

### Primary Keys

Use singular object name plus `_id`:
- `customer_id`
- `security_case_id`
- `campaign_id`

### Foreign Keys

Use referenced object name plus `_id`:
- `customer_id`
- `owner_user_id`, for object-level ownership such as actions, reviews, cases, campaigns, and alerts.
- `primary_security_advisor_user_id`, for the main Security Advisor assigned to a customer.
- `status_id`

### Constraints

Recommended names:
- Primary key: `pk_<table>`
- Foreign key: `fk_<table>_<referenced_table>`
- Unique key: `uk_<table>_<meaning>`
- Check constraint: `ck_<table>_<meaning>`

Examples:
- `pk_customers`
- `fk_customers_primary_sa`
- `uk_customer_contacts_customer_email`
- `ck_actions_due_after_created`

### Indexes

Recommended names:
- `idx_<table>_<column_or_purpose>`

Examples:
- `idx_customers_primary_sa_health`
- `idx_actions_status_due`
- `idx_sec_case_impacts_customer`

## Shared Column Patterns

### Standard Audit Columns

Use these on operational tables:

- `created_by varchar2(255)`
- `created_at timestamp default systimestamp not null`
- `updated_by varchar2(255)`
- `updated_at timestamp`

Optional later improvement:
- Add triggers to populate audit fields from `v('APP_USER')` in APEX.
- For the first build, APEX forms can populate these fields or triggers can be added in a later hardening script.

### Source Columns

Use these where data may later come from integration:

- `source_system varchar2(100)`
- `source_reference varchar2(500)`
- `last_synced_at timestamp`

Use on:
- `customers`
- `interactions`
- `security_events`
- `customer_estate_items`

### Active Flags

Use:
- `active_flag varchar2(1) default 'Y' not null`

Check constraint:
- `active_flag in ('Y','N')`

## Script 03: Core Tables

File:
- `03_core_tables.sql`

Purpose:
- Create the customer, user, contact, estate, engagement, review, and action tables.

### `internal_users`

Purpose:
- Stores Security Advisors, managers, Oracle account team members, and MVP users.

Key relationships:
- Referenced by `customers.primary_security_advisor_user_id`.
- Referenced by `oracle_account_team_members.user_id`.
- Referenced by actions, reviews, cases, campaigns, and alerts as owner fields.

Important columns:
- `user_id`
- `full_name`
- `email`
- `role_name`
- `department`
- `active_flag`

Constraints:
- Unique `email`.
- `active_flag in ('Y','N')`.

### `customers`

Purpose:
- Central portfolio account table.

Important columns:
- `customer_id`
- `customer_name`
- `industry`
- `region`
- `tier_id`
- `status_id`
- `primary_security_advisor_user_id`
- `current_security_contact_id`
- `current_health_status_id`
- `current_health_score`
- `health_score_reason`
- `health_calculated_at`
- `manual_health_override_flag`
- `health_override_reason`
- `health_override_by`
- `health_override_at`
- audit/source columns

Constraints:
- Foreign key to `customer_tiers`.
- Foreign key to `customer_statuses`.
- Foreign key to `internal_users` for the primary Security Advisor.
- Foreign key to `health_statuses`.
- Check `current_health_score between 0 and 100`.
- Check `manual_health_override_flag in ('Y','N')`.

Important implementation detail:
- `current_security_contact_id` references `customer_contacts`, but `customer_contacts` also references `customers`.
- To avoid circular creation issues, create the column first and add the foreign key in `06_constraints_indexes.sql`.

- `create_health_snapshot(p_customer_id number default null)`

Core rule:
- Use an increasing risk scale starting at 0 and capped at 100.
- Add one 30-point contribution when at least one customer estate product maps
  to an Oracle acronym with `SECALERT = TRUE`.
- Set the derived health status to `NEEDS_ATTENTION` when the effective risk
  score is greater than or equal to 30.
- Recalculate contributions idempotently; never increment the stored score on
  each dashboard render or refresh.
- Define and centralize the weights for the remaining engagement, action,
  review, case and campaign signals in `pkg_health_score` before enabling them.

## Implementation Risks

### Circular Foreign Keys

Risk:
- `customers.current_security_contact_id` references `customer_contacts`.
- `actions.campaign_recipient_id` references `notification_campaign_recipients`, which is created later than actions.

Mitigation:
- Add these foreign keys in `06_constraints_indexes.sql` after all tables exist.
- Do not add `notification_campaign_recipients.follow_up_action_id` in the MVP.

### Overbuilt Lookup Tables

Risk:
- Many lookup tables can slow initial build.

Mitigation:
- Keep lookup structure uniform.
- Generate them consistently.
- Load minimal values first.

### Deferred Config Tables

Deferred from MVP:
- `alert_rules`

Reason:
- Initial alert generation should be implemented directly in `pkg_alert_generation`.
- Add configurable alert rules later only if administrators need to maintain thresholds in the app.

### Health Logic Too Complex

Risk:
- Overly complex scoring becomes hard to trust.

Mitigation:
- Start with the MVP rules.
- Always write `health_score_reason`.
- Keep manual override visible.

### Campaign Workflow Ambiguity

Risk:
- Users may create campaigns directly from CVEs and duplicate work.

Mitigation:
- Enforce the workflow in app design:
  `security_event -> security_case -> customer impacts -> campaign`.

### Estate Data Quality

Risk:
- Customer impact matching is only as good as the estate data.

Mitigation:
- Track `last_verified_at`.
- Show stale estate records on customer detail.
- Allow manual add/remove of impacted customers.
